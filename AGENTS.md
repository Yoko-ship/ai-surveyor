# Правила работы с ИИ-сюрвейером INSON

Эти инструкции действуют для всего репозитория. Указания пользователя в текущей задаче имеют приоритет.

## С чего начинать

1. Прочитать `PROJECT.md` — назначение, устройство и границы продукта.
2. Прочитать `docs/RUN_READINESS.md` — проверенные условия запуска и известные ограничения.
3. Прочитать последние записи `WORK_LOG.md` и проверить `git status --short`; сохранять чужие незавершённые изменения.
4. Для конкретной задачи читать соответствующие исходники и документы в `docs/`. `CLAUDE.md` сохраняет прежний контекст; его исторические утверждения о готовности проверять по коду и журналу.

## Обязательный журнал работы

Пользователь попросил сохранять историю всей работы в Markdown. Использовать корневой `WORK_LOG.md` во всех следующих сессиях.

- В начале задачи добавить дату по Asia/Tashkent, запрос и исходное состояние.
- После каждого осмысленного изменения записать **что изменено, в каких файлах и зачем**. Фиксировать также созданные локальные данные и изменения окружения.
- Записывать выполненные проверки и существенные исследовательские действия: команду или способ проверки, результат, ограничения. Не выдавать чтение кода за успешный запуск.
- Перед ответом пользователю дописать итог, незакрытые проблемы и следующий шаг. При прерывании оставлять понятное место продолжения.
- Новые задачи добавлять отдельными записями; не переписывать историю под новый результат. Внутри текущей записи можно уточнять незавершённые пункты.
- Не записывать секреты, пароли, токены, коды первого администратора, персональные данные или содержимое клиентских документов. Ссылаться на файлы вместо копирования больших выводов.
- Изменились назначение или устройство — обновить `PROJECT.md`; условия запуска — `README.md` и `docs/RUN_READINESS.md`.

## Изменения и окружение

- Рабочая платформа — Python/FastAPI, SQLite, обычные HTML/CSS/JavaScript. Штатное окружение Windows: `sandbox/.venv`; версия Python в Dockerfile — 3.12.
- Версии зависимостей закреплены в `requirements.txt`. Не обновлять их попутно и не устанавливать пакеты глобально. Установка пакетов требует разрешения пользователя, если оно ещё не дано (правило существующего `CLAUDE.md`).
- Использовать `PYTHONIOENCODING=utf-8`. Один процесс Uvicorn; расписание встроенное либо отдельное `python -m app.worker`. Оба используют одно хранилище и блокировку планировщика. См. `docs/ARCHITECTURE.md`.
- Не менять тарифы, страховые правила, права доступа или интеграции в рамках задачи по документации/запуску.
- Не публиковать и не отправлять сообщения через Telegram или другие внешние сервисы без соответствующего поручения.
- Очередь `/tasks` и роли агентов из старого `CLAUDE.md` — функции самого продукта. Проверка репозитория и подготовка запуска не требуют работающего сервера или создания задач в его базе.

## Данные и проверки

- `data/surveyor.db` и содержимое `STORAGE_DIR` могут содержать рабочие данные. Не удалять и не пересобирать их автоматически.
- `tools/db_build.py` заполняет/заменяет справочники в **`data/surveyor.db` независимо от `STORAGE_DIR`**. Для нового локального запуска допустима сборка отсутствующей базы; существующую базу сначала изучить и сохранить резервную копию. Не запускать пересборку на базе с пользователями ради тестов.
- Проверки с записью выполнять на копии/отдельной базе. В проекте есть `tests/tmpdb.py`; перед запуском конкретного файла убедиться, что используется изоляция. `STORAGE_DIR` сам по себе не изолирует все скрипты из `tools/`.
- Полный безопасный прогон: `sandbox/.venv/Scripts/python.exe tools/test_all.py`; выборочный — добавить имена файлов тестов. Он собирает отдельную базу и выполняет собственные точки входа скриптов. Прямой запуск отдельных старых тестов требует подготовленных данных; pytest не считать эквивалентным их точкам входа.
- При локальной диагностике выключать фоновые задачи через `SURVEYOR_NO_BACKGROUND=1`, не использовать реальные токены и не запускать сетевые проверки без необходимости.
- `SURVEYOR_DEV=1` предназначен для разработки на своём компьютере. Для такого запуска слушать `127.0.0.1`; на публичном сервере режим выключен.
- После изменения запускать подходящие существующие проверки. В итоговом сообщении разделять: прошло, не прошло, не проверялось и почему.

## Где править интерфейс и логику

- Сборка приложения — `app/application.py`, настройки — `app/config.py`, startup/shutdown — `app/infrastructure/lifecycle.py`. Предметные модули не импортируют `app.main`/`application` и ничего не записывают при импорте.
- Новый код расчёта и запроса добавлять в `app/modules/pricing/` и `app/modules/surveys/`; HTTP делегирует сценарию, сценарий сохраняет связанные строки в одной транзакции. Чистое ядро не импортирует HTTP, базу или модель.
- Новое изменение схемы — следующая версия в `app/infrastructure/migrations.py` с тестом перехода; не запускать `db_build` для обновления рабочей базы. Старые модули переносить по работающим сценариям с сохранением совместимости.

- Мини-приложение: исходники `frontend/tg/`, сборка `python tools/tg_build.py`, контроль `python tools/tg_build.py --check`. Не править только собранный `app/tg.html`.
- Экран агента: `docs/agent_ui.template.html`, данные/сборщик `tools/ui_build.py`; собранный файл — `docs/agent_ui.html`.
- Акт: `app/act.py` — фасад, реализация в `app/act_pkg/`. Юрист и тексты актов также разделены на пакеты; сохранять эти границы.
- Интерфейсы используют тему из `app/theme.js`, общие CSS-переменные и переводы ru/uz/en. Под внешними данными сохранять ссылку на источник.

## Предметные ограничения

- Основной поток: сведения об объекте → фото/документы → оценка риска и расчёт → акт → решение человека. Интеграция с ЕАИС не входит в текущий объём продукта.
- Не удалять классы и продукты из справочников. Ставки проверять отдельно по каждому классу, сохранять версии тарифов и воспроизводимость расчётов.
- Экспертные коэффициенты остаются `calibrated = 0` до подтверждённой калибровки. Не выдумывать недостающие данные страховщика.
- Ограничения кредитных продуктов, РПМ и иных расчётов брать из действующего кода и предметных документов; менять только по отдельному заданию. Ссылку на норму сохранять вместе с проверкой.
- Требование проекта: рабочие персональные данные размещать в Узбекистане. Для демонстраций использовать обезличенные данные. Проверка репозитория не подтверждает юридическую актуальность нормативных ссылок.
- Проектные документы ведутся на русском языке, как существующие материалы. Пользователю отвечать просто и на языке его запроса.
