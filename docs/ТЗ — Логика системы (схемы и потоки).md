# ИИ-сюрвейер: техническое задание. Логика системы

Версия от 01.10.2026. В документе только логика: что как должно работать и с чем взаимодействует. Способ реализации выбирает программист.

## 1. Назначение

Сотрудник страховой компании загружает фото и документы объекта и получает сюрвейерский акт с вилкой ставки. Система опирается на тарифы компании и на открытые данные: статистику, рынок, законы, цены. Решение принимает андеррайтер.

Что с чем взаимодействует:

| Часть | Получает | Отдаёт |

| Мини-приложение | Фото, документы, четыре поля от сотрудника | Акт на экране, Word, PDF |
| Админ-панель | Сотрудники, продукты, тарифы, страховые случаи | Справочники для ядра |

| Telegram-бот | Готовый акт | Файл в чат сотрудника |

## 3. Потоки

### 3.1. Формирование акта

```
 1. Сотрудник загружает фото и документы
    ↓
 2. Система определяет вид каждого файла:
    фото объекта / договор / запрос филиала / отчёт
    ↓
 3. Файл с текстом  → читают правила
    Фото или скан   → читает языковая модель
    ↓
 4. Сотрудник видит распознанное с пометкой
    «откуда взято», исправляет при необходимости
    ↓
 5. Сотрудник вводит: продукт, страховую сумму,
    стоимость объекта, регион
    ↓
 6. Система считает ставку и премию (поток 3.3)
    ↓
 7. Система берёт открытые данные по региону
    и классу (поток 3.5) и строит вилку ставки
    ↓
 8. Система сверяет документы с расчётом
    и подбирает оговорки по шаблону класса
    ↓
 9. Акт: экран → Word → PDF → бот в Telegram
```

### 3.2. Чтение документа

```
 1. Файл получен
    ↓
 2. Проверка: формат, размер, число страниц
    не подходит → отказ с понятной причиной
    ↓
 3. Есть текстовый слой?
    ├─ да  → разбор правилами, без языковой модели
    └─ нет → языковая модель читает как картинку
    ↓
 4. Определение вида документа по заголовку
    и набору строк
    ↓
 5. Извлечение значений: суммы, сроки, тариф,
    объект, стороны (только организации)
    ↓
 6. Пустое поле бланка → «не заполнено»
    Нет в документе   → «данные недоступны»
    ↓
 7. Значения разных источников сравниваются,
    расхождения отмечаются
```

### 3.3. Расчёт ставки и премии

```
 1. Берём ставку продукта из тарифной политики
    и ТИП СТАВКИ, заданный администратором
    ↓
 2. Определяем уровень риска по признакам объекта:
    низкий / умеренный / высокий
    ↓
 3. Применяем поправку по уровню риска
    ↓
 4. Проверяем минимум: ставка не ниже минимальной
    ↓
 5. Считаем премию по типу ставки:
    ├─ ГОДОВАЯ:
    │  премия = сумма × ставка × дни срока / 365
    └─ ФИКСИРОВАННАЯ:
       премия = сумма × ставка (срок не влияет)
    ↓
 6. Строим вилку ставки:
    минимальная → рекомендуемая → рыночная
    ↓
 7. Сравниваем с тарифом из запроса или договора:
    ниже минимума / внутри вилки / выше рынка
```

Пример различия. Страховая сумма 100 000 000 сум, ставка 0,5 %, срок 3 года:

| Тип ставки | Расчёт | Премия |
|---|---|---|
| Годовая | 100 000 000 × 0,5 % × 1 095 / 365 | 1 500 000 сум |
| Фиксированная | 100 000 000 × 0,5 % | 500 000 сум |

Правила для фиксированной ставки:

1. Срок договора на премию не влияет.
2. Для сравнения с рынком фиксированная ставка пересчитывается в годовую: ставка × 365 / дни срока. В акте показываются обе.
3. Сверка с запросом филиала идёт по той формуле, которая задана для продукта.
4. У обязательных видов тип ставки задаёт нормативный акт.

### 3.4. Оценка стоимости объекта

```
 1. Сотрудник ввёл заявленную стоимость
    ↓
 2. Выбор способа по виду объекта и сумме:
    ├─ автомобиль      → открытые объявления
    ├─ техника, жильё  → объявления по снимку экрана
    ├─ оборудование    → цена покупки − износ
    └─ крупный объект  → отчёт оценщика
                         + проверка вторым способом
    ↓
 3. Отбор: то же изделие, не старше 6 месяцев,
    цена и дата есть
    ↓
 4. Отбрасываем слишком дешёвые и слишком дорогие
    ↓
 5. Средняя цена и вилка
    ↓
 6. Расхождение с заявленной больше 15 %?
    ├─ нет → стоимость подтверждена
    └─ да  → «стоимость нужно уточнить»
    ↓
 7. В акте: оценка, источник, дата,
    правки сотрудника
```

### 3.5. Сбор открытых данных

```
 1. Расписание запускает сбор по каналу
    (раз в сутки или по запросу)
    ↓
 2. Проверка: сайт разрешает автоматический доступ?
    ├─ нет → канал не используется,
    │        данные загружает сотрудник
    └─ да  ↓
 3. Получение: открытый файл / страница сайта
    ↓
 4. Проверка формата: те же колонки и поля?
    ├─ нет → канал отключается,
    │        сообщение администратору
    └─ да  ↓
 5. Приведение к единому виду: показатель,
    регион, период, значение, единица
    ↓
 6. Сохранение с датой получения и ссылкой
    ↓
 7. Сравнение с прошлой версией:
    изменилось → новая версия, старая в истории
    ↓
 8. Использование в акте:
    под каждой цифрой — источник и дата
```

Если сайт недоступен, система берёт последние сохранённые данные и показывает их дату.

### 3.6. Админ-панель: добавление сотрудника

```
 1. Администратор открывает «Сотрудники → Добавить»
    ↓
 2. Вводит: Ф.И.О., должность, департамент или
    отдел, филиал, логин, пароль, телефон, роль
    ↓
 3. Проверка: логин и телефон уникальны,
    пароль не короче 8 знаков
    ↓
 4. Сотрудник создан, запись в журнале
    ↓
 5. Первый вход сотрудника → смена пароля
    ↓
 6. Сотрудник видит только то,
    что разрешено его роли
```

### 3.7. Админ-панель: добавление продукта

```
 1. Администратор открывает «Продукты → Добавить»
    или загружает файл Excel
    ↓
 2. Вводит: код, название, класс, ставку,
    минимальную ставку, дату начала действия
    ↓
 3. ВЫБИРАЕТ ТИП СТАВКИ из списка:
    ├─ годовая
    ├─ фиксированная
    ├─ по программе
    └─ по нормативному акту
    ↓
 4. Проверка: код уникален, ставка не ниже
    минимальной, тип ставки выбран
    ↓
 5. При импорте — предпросмотр:
    добавится / изменится / ошибки по строкам
    ↓
 6. Сохранение новой версией: старый тариф остаётся
    для актов, сформированных до даты изменения
    ↓
 7. Продукт появляется в мини-приложении
    и считается по своему типу ставки
```

Для продуктов, уже заведённых в справочник, тип ставки по умолчанию — «годовая». Администратор проверяет список и меняет тип там, где ставка фиксированная.

### 3.8. Админ-панель: страховые случаи

```
 1. Администратор загружает данные за 3 года:
    год, код продукта, название,
    число страховых случаев, сумма выплат
    ↓
 2. Проверка: продукт есть в справочнике,
    числа не отрицательные
    ↓
 3. Предпросмотр → подтверждение → сохранение
    ↓
 4. Сводка по продукту: случаи и выплаты по годам
    ↓
 5. Если загружены премии и число договоров:
    убыточность = выплаты / премии
    частота     = случаи / договоры
    ↓
 6. Акт показывает убытки по продукту за 3 года
    ↓
 7. После утверждения актуарием — убыточность
    продукта влияет на рекомендуемую ставку
```

## 5. Правила работы с открытыми данными

1. Сайт запрещает автоматический доступ — парсинг не ставится. Защита не обходится.
2. Программа представляется своим именем, запрашивает не чаще раза в секунду, при отказе не повторяет запрос.
3. Каждая цифра хранится с датой получения и ссылкой на источник.
4. В запросы к внешним сайтам не попадают имена клиентов, адреса и другие персональные данные.
5. Открытые данные влияют на рекомендуемую ставку только в заданных границах и никогда не опускают её ниже минимальной.
6. Все поправки по открытым данным помечены «экспертные, не утверждены страховщиком», пока их не утвердит актуарий.
7. Данные старше установленного срока показываются с пометкой «устарели».

## 6. Возникающие проблемы

| № | Проблема | Чем грозит | Решение |
|---|---|---|---|
| 1 | Сайт закрыт от программ (OLX) | Нет цен для оценки | Снимок экрана от сотрудника; договор с площадкой |
| 2 | Сайт изменил устройство страниц | Канал отдаёт неверные цифры | Проверка формата при каждом сборе, отключение канала, сообщение администратору |
| 3 | Данных нет в разрезе регионов (пожары, ЧС) | Поправка региона для имущества слабая | Запросить данные у ведомства; до этого — без поправки |
| 4 | Данные публикуются с опозданием | Ставка опирается на прошлый год | Показывать период; пометка «устарели» |
| 5 | Показатель не подходит объекту (жилой фонд для оборудования) | Неверная поправка | Набор показателей задаётся по виду объекта в шаблоне класса |
| 6 | Поправки и доли рисков — оценка разработчика | Ставка не отражает опыт компании | Загрузить страховые случаи за 3 года, утвердить актуарием |
| 7 | Все ставки считаются как годовые | Премия по фиксированным ставкам завышена на многолетних договорах | Тип ставки у продукта (поток 3.7) |
| 8 | Тариф «по программе» у части продуктов | Акт пишет «ставка не определена» | Завести ставки программ в справочник |
| 9 | Сервер за рубежом | Нельзя вести данные клиентов и сотрудников | Сервер в Узбекистане |
| 10 | Языковая модель на бесплатном тарифе | Чтение фото отключается при превышении предела | Платный тариф |
| 11 | Скан документа с данными людей уходит в языковую модель | Нарушение правил о персональных данных | Только документы организаций; модель на своём сервере |
| 12 | Источник недоступен из-за рубежа | Канал не работает на тестовом сервере | Проверить с сервера в Узбекистане |
| 13 | Настоящих договоров и отчётов для проверки нет | Точность чтения не подтверждена | Передать образцы |
| 14 | Сайт недоступен в момент формирования акта | Акт без свежих данных | Последние сохранённые данные с датой |

## 7. Порядок работы

| № | Работа | Результат |
|---|---|---|
| 1 | Тип ставки у продукта: выбор в админке, расчёт премии, пересчёт в годовую для сравнения | Фиксированные ставки считаются верно |
| 2 | Админ-панель: сотрудники, продукты с импортом, страховые случаи | Потоки 3.6–3.8 работают |
| 3 | Вилка ставки с поправками региона и рынка — выложить | Поток 3.3 полностью на сервере |
| 4 | Проверка новых каналов: разрешён ли доступ, в каком виде данные | Список «подключаем / нельзя / нужен договор» |
| 5 | Подключение разрешённых каналов по важности: сейсмика, погода, торги, биржа, строительство | Поток 3.5 по каждому каналу |
| 6 | Убытки компании в рекомендуемой ставке после утверждения актуарием | Ставка опирается на данные компании |
| 7 | Перенос на сервер в Узбекистане, приёмка | Рабочий запуск |
