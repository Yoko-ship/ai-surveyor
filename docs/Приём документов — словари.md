# Приём документов — словари

Данные для `app/ingest.py` (единый приём PDF/DOCX/XLSX/изображений → таблица `document_extracts`).
Всё лежит в одном файле **`docs/ingest_dicts.json`**. Код разбора пишет разработчик, здесь — только
словари, пороги и регулярки. Задача 97 (родительская 95), подготовил аналитик данных, 20.09.2026.
Правка по замечаниям контролёра от 20.09.2026 (английские документы, `mixed` на русском бланке,
дата оценки) — раздел 6 в конце заметки. Вторая правка того же дня (учебник опознавался как
договор) — раздел 7. Третья правка 21.09.2026 (русский и узбекский бланк полиса и выписки
уходили в «прочее») — раздел 8. Там же, в 8.3, — правило строки-заголовка для маркеров
`"head": true`, которое разработчик реализовал в `app/ingest.detect_kind` 21.09.2026.
**Заметка сверена с кодом повторно вечером 21.09.2026**, после того как разработчик добавил
`ingest._is_blank_title`: маркеру с флагом `head` теперь мало стоять в строке-заголовке — нужно,
чтобы значащих слов сверх маркера в строке не было вовсе и чтобы у документа нашёлся **второй
признак бланка** (номер в той же строке или не меньше двух заполненных реквизитов). Все числа
в разделах 2, 8.2 и 8.3 — прогон этой редакции кода. Единственная правка словаря при этой сверке:
флаг `"head": true` проставлен английским маркерам `insurance policy` и `insurance contract`
(вес 3, см. 8.3); веса, пороги и `norm_weight` не менялись.

## Что внутри JSON

| Ключ | Что это |
|---|---|
| `lang` | четыре словаря служебных слов (ru 149, uz-latn 128, uz-cyrl 129, en 115), буквенные маркеры, `rules` — алгоритм и пороги |
| `doc_kinds` | 6 видов документов + «прочее»: маркеры с весами по языкам (ru 116, en 138, uz-latn 83, uz-cyrl 69; счёт на 21.09.2026), `header_markers` для XLSX, порог `threshold` |
| `doc_kinds_scoring` | формула уверенности и защитные правила |
| `doc_kinds_disambiguation` | что делать, когда совпали два вида |
| `patterns` | 29 регулярок (Python `re`): деньги, даты, VIN, кадастр, госномер, ИНН/ОКЭД, площади, проценты, адрес |
| `patterns_meta` | для каждой регулярки: примеры, на чём проверена, чем опасна, ссылки на PD-правила |
| `fields` | только поля, которых нет в `docparse.FIELDS` (штатка, выписка, отчёт оценщика) |
| `facts` | булевы признаки (ипотека, арест, полис, нужен OCR, найдены персональные данные) |

## Что берём из существующего кода, а не дублируем

* `docparse.norm()` и `docparse.APOSTROPHES` — нормализация текста (нижний регистр, ё→е, шесть видов
  апострофа → `'`). Все словари уже записаны в нормализованном виде.
* `docparse.FIELDS` — подписи полей техпаспорта и кадастра на ru/uz-latn/uz-cyrl. В словарях их нет.
* `docparse.REGIONS` — 14 областей + Ташкент; адрес разбираем ими, в JSON только маркеры
  улицы/дома/махалли (`address_marker`).
* `docparse.PERSONAL_LABELS` / `is_personal_label()` — строки с персональными данными.
* `docparse.MIN_TEXT_CHARS` и статус `ST_OCR` — признак «скан без текстового слоя».
* `llm.py PD_RULES` — оттуда взяты шаблоны кадастрового номера, госномера ТС и телефона.

## 1. Язык

Скоринг без сторонних пакетов: `score = доля служебных слов × скриптовый множитель + буквенный бонус`.
Буквенные маркеры: **uz-cyrl** — ў, қ, ғ, ҳ; **ru** — ы, щ, ь (их нет в узбекской кириллице);
**uz-latn** — только сочетания `o'`, `g'` и узбекские окончания `-lar, -lari, -larni, -larning,
-ning, -ida, -idan, -dagi, -gacha, -ligi, -uvchi, -ishi` (правка 20.09.2026, см. раздел 6:
сочетания `sh, ch, ng, q, x` и короткие окончания `-ga, -da, -ni, -chi, -siz, -gan, -dan` убраны,
коэффициент бонуса снижен с 4.0 до 2.0); **en** — только по словарю.
Латинские имена собственные (марка и модель авто, название банка), VIN, госномер и числовые коды
языка не имеют и признаком узбекской латиницы не считаются. Пороги: `min_tokens = 8`, `min_score = 0.06`, `mixed_threshold = 0.6`
(второй язык набрал ≥ 60 % от первого → `mixed`), меньше `min_score` → язык **не определён (null)**,
а не «ru по умолчанию». Для длинных и табличных файлов считаем по строкам/ячейкам и берём язык,
у которого ≥ 70 % строк, иначе `mixed`.

длиной 1–2 символа > 0.5 лучше ставить `null`.

## 2. Вид документа

`confidence = min(1, сумма весов совпавших маркеров / norm_weight)`, `norm_weight = 8`
(у отчёта оценщика 9), порог принятия **0.55** (был 0.4; поднят 20.09.2026, см. раздел 7). Маркеры короче 4 символов ищутся по границе слова.

**Вес позиции маркера** (`app/ingest.detect_kind`, редакция 21.09.2026): строка-заголовок бланка
**×2.0**, шапка **×1.5**, остальной текст **×1.0**, имя файла **×0.5** (имя даёт клиент — это
подсказка, а не документ). Строка-заголовок — первые `BLANK_HEAD_LINES` = 3 непустые строки
текста (плюс название листа XLSX и первые 3 строки листа) при условии, что кроме самого маркера
в строке не больше `BLANK_HEAD_REST` = 4 слов. Шапка — первые `HEAD_LINES` = 40 строк текста
или первые `HEADER_ROWS` = 5 строк листа XLSX.

**Двух границ две, и путать их нельзя:**

| Граница | Константа | Для чего |
|---|---|---|
| 40 строк текста (5 строк листа XLSX) | `HEAD_LINES` / `HEADER_ROWS` | докуда действует «шапка» для маркера с весом ≥ 4 и докуда `_blank_requisites` ищет заполненные реквизиты бланка |
| 3 непустые строки | `BLANK_HEAD_LINES` | докуда действует «строка-заголовок» для маркера с флагом `"head"` |

Бонус ×2.0 за положение и право `head`-маркера считаться **сильным** — разные вещи, и условия
у них с 21.09.2026 разные: ×2.0 даёт любая строка-заголовок (≤ 4 слов сверх маркера), а сильным
`head`-маркер становится только через `ingest._is_blank_title` (см. ниже).

Оговорка про `header_markers`: этот список в словаре — **справочные данные**, в подсчёте
уверенности он не участвует (`app/ingest._kind_defs`, поле `headers`). Виды, которые опознаются
по шапке таблицы, — штатное расписание («должность / кол-во штатных единиц / оклад / фонд оплаты
труда», `lavozim / birliklar soni / ish haqi fondi`) и выписка («дата / дебет / кредит / остаток
/ назначение платежа», `debet / kredit / qoldiq / to‘lov maqsadi`) — ловятся обычными маркерами
из `markers`, которым шапка листа даёт ×1.5, а название листа — ×2.0.

Английские маркеры доведены до уровня русских по всем семи видам 20.09.2026 — см. раздел 6.1.

Защита от ложных срабатываний: если не совпал ни один «сильный» маркер, уверенность
делится пополам — а значит, не может превысить 0.5 и при пороге 0.55 вид не принимается вовсе.
Читается это так: **вид документа ставим по формулировке бланка, а не по теме текста**. Без этого
любой длинный текст со словами «договор», «стороны», «страховщик» становился договором с
уверенностью 1.0.

Сильным считается (редакция кода 21.09.2026, `app/ingest.detect_kind`):

* маркер с весом ≥ 4, найденный **вне глубины текста** — в строке-заголовке, в шапке, в шапке
  листа XLSX или в имени файла. Оговорка «вне глубины текста» важна: те же слова, стоящие
  на 554-й строке длинного документа, — это упоминание, а не бланк (см. 8.2, Тарифная политика);
* маркер с флагом `"head": true` — **только в строке-заголовке, и только если эта строка прошла
  проверку `ingest._is_blank_title`**. Проверка требует ОБОИХ условий:
  1. строка действительно заголовок: кроме самого маркера значащих слов в ней **нет** (допустимы
     цифры, короткие коды вроде `AB`, слова «серия/номер» в четырёх написаниях);
  2. у документа есть **второй признак бланка**: номер в той же строке (`№`, `#`, `No.`,
     `seriya`, `raqami`) **либо** не меньше `BLANK_REQUISITES_MIN` = 2 заполненных реквизитов
     из `ingest.BLANK_REQUISITE_LABELS` в первых 40 строках.

  Реквизит засчитывается только как **«метка + разделитель + число»**: «Страховая сумма:
  100 000 000 сум» — да, «страховая сумма в примере 100 000 000 сум рассчитана условно» — нет.
  Требование значения не придирка: без него учебник с такой фразой в оглавлении снова становился
  договором 1.000. Разбор в разделе 8.3.

Вес ≥ 4 может быть только у заголовка бланка или договорной формулы
(`technical passport`, `cadastral passport`, `valuation report`, `bank statement`,
`have concluded this contract`, `hereinafter referred to`, `insurance policy no`,
«именуемый в дальнейшем», «заключили настоящий договор»). Общие термины страхования
(`insurance contract`, `insurance policy`, `sum insured`, `policyholder`, `the insurer`,
`the parties`, «предмет договора», «страховщик») — только слабые: они есть в любом учебнике
и в любом нормативном акте. Флаг `"head"` этого не отменяет: `insurance policy` и
`insurance contract` остаются маркерами с весом 3 и в глубине текста слабы — флаг лишь разрешает
им сработать в проверенной строке-заголовке заполненного бланка.

Штраф ×0.7 за маркер чужого языка к строке-заголовку **не применяется**: двуязычный бланк для
РУз — норма (ОСГО по ПКМ № 141 печатают сразу на латинице и по-русски). Проверено 21.09.2026:
«СТРАХОВОЙ ПОЛИС № AB 0001234» над узбекским текстом даёт договор **0.750**, а не «прочее».

Две ловушки поиска маркеров, обе проверены на текстах проекта:
* `docparse.fold()` убирает точки, `№` и дефисы — маркер `insurance contract №` сворачивается
  в `insurance contract` и совпадает с чем угодно. Маркеры пишем только словами;
* переносы строк к моменту поиска уже стали пробелами, поэтому короткий хвост маркера
  склеивается со следующим словом: `insurance contract no` совпадало с «insurance contract
  **not**» в `book_Reinsurance.txt`.

Проверка на 11 синтетических образцах (реальных бланков в проекте нет) — все 11 определены верно,
уверенность 1.0. Разбор совпадений: «выписка из государственного реестра прав» даёт 1.0 сразу по
двум видам (кадастр и выписка) — правило разрешения: есть «кадастровый номер / kadastr raqami /
кадастр рақами» → вид «кадастр», факт `is_register_extract = true`.

**Нормативные акты и учебники** (`docs/source/*.txt`) дают «прочее»: сильных бланковых
формулировок в шапке у них нет, а общей лексики хватает только на 0.5 — ниже порога 0.55.
С 21.09.2026 это верно для **всех 12** файлов, включая `Тарифная политика.txt` (раньше —
техпаспорт 1.000, см. 8.2). Отчёт НАПП (`report.md`) даёт максимум 0.19 → «прочее», это
правильно.

Известное ограничение: бланк, заголовок которого стоит глубже 3-й непустой строки (сшитый пакет
документов), по одному голому заголовку вида не получит. Дальше всё зависит от того, **какие у
бланка реквизиты**, а не от того, на какой строке стоит заголовок:

* если в бланке есть хотя бы один реквизит с весом ≥ 4 («Страховой полис серия», «Номер
  полиса», «Подписи и печати сторон»), вид ставится, пока **этот реквизит** попадает в первые
  40 строк текста (`HEAD_LINES`, считаются все строки файла, включая пустые). Глубже 40-й
  строки сильных маркеров нет — вид указывает агент вручную;
* если у бланка только слабые реквизиты (объект страхования, страховая сумма, страховая
  премия, срок страхования — все вес 2–3), единственный источник «сильного» — сам заголовок
  с флагом `head`, а он читается только в первых 3 непустых строках (`BLANK_HEAD_LINES`).
  Такой бланк теряет вид уже с 4-й непустой строки, и 40 строк тут ни при чём.

Второе ограничение, появившееся 21.09.2026 вместе с `_is_blank_title`: **голый заголовок без
номера и без двух заполненных реквизитов вида не даёт вообще**. «СТРАХОВОЙ ПОЛИС / Ташкент» —
прочее 0.000 (кандидат договор 0.375), `INSURANCE CONTRACT` без номера и реквизитов — прочее
0.000 (кандидат договор 0.500). Это плата за то, что заявление, прайс-лист, счёт-фактура, акт,
служебная записка и оглавление не закрывают чужим файлом обязательный пункт чек-листа «Документ
о праве на объект». Бланк без номера и без реквизитов — вырожденный случай: вид ставит агент.

Тонкость счёта реквизитов (`ingest._blank_requisites`): реквизит — это **метка + разделитель +
число рядом**. Прогон 21.09.2026: «Страховая сумма: 100 000 000 сум» + «Страховая премия:
1 200 000 сум» → 2 (порог взят); `Sum insured:` + `Insurance premium:` → 2; «Объект страхования:
склад по адресу г. Ташкент» + «Страховая сумма: …» → **1** (у «объекта страхования» значение
текстовое, числа рядом с разделителем нет); те же суммы прозой («страховая сумма в примере
100 000 000 сум рассчитана условно») → **0**.

Проверено прогоном `detect_kind` 21.09.2026 на двух синтетических бланках полиса:

| Заголовок на строке | Бланк с сильным реквизитом | Бланк только со слабыми |
|---|---|---|
| 1-й | договор 1.000 | договор 1.000 |
| 3-й | договор 1.000 | договор 1.000 |
| 4-й | договор 1.000 | **прочее 0.000** (кандидат договор 0.500) |
| 6-й | договор 1.000 | прочее 0.000 (кандидат договор 0.500) |
| 21-й | договор 1.000 | прочее 0.000 (кандидат договор 0.500) |
| 46-й | прочее 0.000 (кандидат договор 0.500) | прочее 0.000 (кандидат договор 0.500) |

Граница «40 строк» привязана к сильному реквизиту, а не к заголовку. Прогон без заголовка вообще,
один сильный реквизит («Страховой полис серия AB номер 0001234») на N-й строке: 1-я, 21-я, 39-я,
**40-я** — договор 1.000; **41-я** и 46-я — прочее 0.000. Прежняя формулировка «опознаётся, пока
заголовок укладывается в первые 40 строк» верна только для бланков первого типа и недействительна.

## 3. Поля и факты

Регулярки написаны под Python `re`, все скомпилированы и прогнаны на примерах
(скрипты проверки — в рабочем каталоге сессии, в проект не клались).

Проверено на реальных текстах: даты `дд.мм.гггг` — 56 и 112 совпадений в актах 1806/1882,
`гггг-мм-дд` — 68 в `Страх_отчет*/report.md` (xlsx отдаёт «2025-07-01 00:00:00»),
`2024 йил 12 сентябр` — 62 совпадения в узбекской редакции акта, `2024-yil 1-may` — 11 в положении
об агентах, проценты — 42 совпадения, деньги — `8,3 trln. so‘m` и ещё 5 в отчёте НАПП,
единица измерения в шапке колонки (`mln. so‘mda`) — 34 совпадения там же.

Важное про деньги: в XLSX сумма чаще всего стоит **без валюты**, а единица вынесена в заголовок
колонки. Поэтому отдельный шаблон `money_unit_header` — сначала ищем единицу в шапке, затем
умножаем числа из ячеек. Форматы: `1 200 000,00 сум`, `1 200 000 so‘m`, `12,5 млн сум`,
`500 тыс. сум`, `1 200 000 сўм`, `UZS 1 200 000`, `6,1 trln. so‘m` — все ловятся.

**Ненадёжно и не подтверждено документом:**

1. **Кадастровый номер.** Формата в нормативных актах нет (см. «Документы объекта — поля для
   автозаполнения.md»: образцов бланка нет, в ЗРУ-803 формат не описан). Шаблон взят из
   `llm.py PD_RULES` — 2–7 числовых групп через двоеточие, пример `10:09:05:01:0123:0001`.
   Он же совпадает с временем вида `10:09:05:01`, поэтому применять только рядом с подписью поля
   (`cadastre_no_labeled`) или при числе групп ≥ 4. **Перед продом сверить с реальным паспортом.**
2. **VIN.** Реального VIN в проекте нет — проверено на синтетических примерах. Класс
   `[A-HJ-NPR-Z0-9]` исключает I, O, Q; дополнительно требуется минимум 3 буквы, иначе шаблон ловил
   17 цифр подряд из длинных дробей в `data/parsed/.../1.1.csv` (5 ложных срабатываний).
   В `docparse.cast('vin')` шаблон намеренно мягче (9–17 символов) — там он обслуживает ещё и
   номера кузова, шасси, двигателя.
3. **ОКЭД, номер счёта (20 цифр), МФО (5 цифр), номер договора** — ни одной выписки и ни одного
   штатного расписания в проекте нет, шаблоны проверены только на синтетике.
4. **Госномер ТС** — шаблон из `docparse.cast('reg_no')` и `llm.py`, но реальных примеров нет;
   оба формата (`01 A 123 AB` и `01 123 ABC`) на документах не сверены.
5. **Порядок шаблонов даты важен.** Для поля-даты шаблоны применяются строго по списку
   `patterns_meta.date.priority`: сначала полные даты (`дд.мм.гггг`, `гггг-мм-дд`, словесные
   ru/uz), и только если ни один не подошёл — одиночный `year`. Значение поля — всё совпадение
   целиком, а не отдельная группа. Год в шаблонах дат лежит в группе `yyyy`; группа `y` осталась
   только в шаблоне `year` (правка 20.09.2026, раздел 6).
6. **Дата словами по-узбекски кириллицей** совпадает и с русскими датами («12 января» ⊂ `январ\w*`):

7. **Сумма без валюты и без множителя** — обычное число; валюту брать из шапки документа, иначе
   поле оставлять пустым. Не подставлять «сум» по умолчанию.

### 8.3. Голый заголовок бланка: почему словарём это не лечилось и как решено правилом строки-заголовка

На момент правки словаря четыре примера оставались «прочим»: голый заголовок без остальных
реквизитов бланка — «СТРАХОВОЙ ПОЛИС № ...», «ДОГОВОР СТРАХОВАНИЯ № ...»,
`SUG'URTA POLISI № ...`, `SUG'URTA SHARTNOMASI № ...`. Словарём это не лечится, и вот
доказательство.

Чтобы такой пример прошёл порог, нужен сильный маркер, а единственные слова в нём — «страховой
полис», «договор страхования», «страховая сумма», «страховая премия». Все они есть и в
`book_Шариатские_стандарты.txt` (24.8 весовых единиц слабых маркеров при `norm_weight` = 8), и в
ПКМ 1882 (15.0), и в Положении 3571 (16.1). Ни при каких весах разделить нельзя: пусть
`W1` — вес «страхового полиса», `W2` — вес «договора страхования», `T` — порог в весах. Бланк
даёт заголовок отдельной строкой (позиционный вес `p > 1`), учебник — те же слова в тексте
(×1.0) плюс свои 24.8: `p·W1 >= T`, `p·W2 >= T`, `W1 + W2 + 24.8 < T`. Из первых двух
`T <= p·min(W1,W2)`, из третьего `T > W1 + W2 + 24.8`; при любом `p <= 2` вместе это даёт
`W1 + W2 > 24.8 + W1 + W2` — неравенство без решений. То же и для узбекских актов.
Существенно здесь не значение `p`, а то, что **вес позиции один и тот же для бланка и для
учебника, если маркер стоит в одном и том же месте**: разделить их может только различие мест,
а не различие весов.

**Разделяет их только положение в документе**: у бланка заголовок стоит отдельной строкой в
самом начале, у учебника те же слова лежат внутри фразы в тексте. Строки-заголовки всех 12
файлов `docs/source/*.txt` от «страхового полиса», «договора страхования» и `sug'urta polisi`
чисты — проверено 21.09.2026.

Поэтому в словаре у четырёх маркеров — «страховой полис» (ru), «договор страхования» (ru),
`sug'urta polisi`, «суғурта полиси» — был проставлен флаг `"head": true` (вечером 21.09.2026
к ним добавились английские `insurance policy` и `insurance contract`, итого **шесть** маркеров,
все с весом 3 — см. ниже), а в
`doc_kinds_scoring.head_marker_proposal` записано предложение разработчику:

> маркер с `"head": true`, найденный в шапке (первые 40 строк или шапка листа xlsx),
> засчитывать сильным; в тексте — нет.

**Предложение принято и реализовано 21.09.2026, но в более узком виде, чем я предлагал.** Первая
редакция и правда считала шапкой первые 40 строк, и на ней у меня были числа 0.562 и 0.938.
Тем же вечером разработчик сузил правило: шапка бланка — это **строка-заголовок**, а не «первые
40 строк». Причина: под «первые 40 строк» попадали оглавление учебника, акт сверки со ссылкой на
полис и служебная записка «прошу выдать страховой полис и оформить договор страхования» — все
они получали «договор 1.000».

**Тем же вечером правило сузили ещё раз** — появилась функция `ingest._is_blank_title` и
константа `BLANK_REQUISITES_MIN = 2`. Причина: одной строки-заголовка мало. «ЗАЯВЛЕНИЕ / Прошу
заключить договор страхования склада», «ПРАЙС-ЛИСТ / Страховой полис (бланк) — 5 000 сум»,
«СОДЕРЖАНИЕ / 1. Страховой полис … 5» тоже кладут маркер в первые три строки, и слов сверх
маркера у них не больше четырёх.

Актуальное определение (`app/ingest.py`, константы, `_in_blank_head`, `_is_blank_title`,
`_blank_requisites`):

* `BLANK_HEAD_LINES = 3` — строка-заголовок ищется в первых **3 непустых** строках текста
  (а для XLSX — ещё в названии листа и первых 3 строках листа);
* `BLANK_HEAD_REST = 4` — кроме самого маркера в этой строке допускается не больше **4 слов**
  (это условие даёт позиционный бонус ×2.0, но ещё не делает маркер сильным);
* `_is_blank_title` — маркер с флагом `head` признаётся **сильным**, только если выполнены ОБА
  условия:
  1. кроме самого маркера значащих слов в строке **нет** — допускаются цифры, короткие коды
     вроде `AB` и слова «серия/номер» в четырёх написаниях (`_BLANK_SERVICE_RE`,
     `_BLANK_NUM_WORDS`);
  2. есть **второй признак бланка**: номер в той же строке (`№`, `#`, `No.`, `seriya`, `raqami`
     — `_has_blank_number`) **либо** не меньше `BLANK_REQUISITES_MIN` = 2 заполненных реквизитов
     из `ingest.BLANK_REQUISITE_LABELS` в первых 40 строках (`_blank_requisites`).

Реквизит — это **метка + разделитель + число рядом**, и требование значения принципиально: без
него фраза «страховая сумма в примере 100 000 000 сум рассчитана условно» считалась бы
реквизитом, и учебник снова становился договором 1.000.

Поэтому «СТРАХОВОЙ ПОЛИС № AB 0001234» засчитывается (после маркера остаются «ab» и «0001234» —
служебные, «№» убирает `fold()`, и он же второй признак), а «Прошу выдать страховой полис и
оформить договор страхования», «Страховой полис (бланк) — 5 000 сум» и «СТРАХОВОЙ ПОЛИС /
Ташкент» — нет: у первых двух есть значащие слова сверх маркера, у третьего нет второго признака.

Маркеры разбираются пятым элементом `head_only`, место находки определяется как «шапка бланка»,
«шапка», «текст» или «имя файла», и сильным маркер признаётся по условию

> `if (w >= 4 and where != "текст") or (head_only and where == "шапка бланка"`
> `        and _is_blank_title(marker, blank_head, requisites)):`

Здесь две независимые ветви. Первая: обычный сильный маркер (вес ≥ 4) больше не засчитывается
в глубине текста — именно это починило `Тарифная политика.txt` (см. 8.2). Вторая: маркер с
`"head": true` силён только в проверенной строке-заголовке заполненного бланка, а в остальном
тексте остаётся слабым с весом 3 — и учебник о страховании или нормативный акт вида по-прежнему
не получает. Кода я не касался, его написал разработчик; я проверил поведение прогонами.

Что дало правило строки-заголовка (прогон `app/ingest.detect_kind` 21.09.2026):

| Голый заголовок | Было с «первыми 40 строками» | Стало со строкой-заголовком |
|---|---|---|
| «СТРАХОВОЙ ПОЛИС № AB 0001234» | договор 0.562 | договор **0.750** |
| «СТРАХОВОЙ ПОЛИС № AB 0001234» над узбекским текстом | прочее 0.000 | договор **0.750** |
| «ДОГОВОР СТРАХОВАНИЯ № 12» | договор 0.938 | договор **1.000** |
| `SUG'URTA POLISI № AB 0001234`, «СУҒУРТА ПОЛИСИ № AB 0001234» | договор 1.000 | договор **1.000** |
| `SUG'URTA SHARTNOMASI № 12`, «СУҒУРТА ШАРТНОМАСИ № 12» | прочее 0.000 (договор 0.500) | прочее 0.000 (договор 0.500) |
| `INSURANCE POLICY No. AB 0001234` | договор 1.000 | договор **1.000** (сильный маркер `insurance policy no`, вес 4) |
| `INSURANCE CONTRACT No. 12` | прочее 0.000 (договор 0.500) | договор **1.000** — только после флага `head` 21.09.2026, см. ниже |

Запас над порогом 0.55 у самого слабого принимаемого примера вырос с **0.012** до **0.20** —
это важнее самих чисел: раньше любая правка веса на единицу роняла бланк полиса обратно
в «прочее». Двуязычный случай починен тем, что штраф ×0.7 за маркер чужого языка к
строке-заголовку не применяется (ОСГО по ПКМ № 141 печатают на двух языках сразу).

Нерешённым честно остаётся одно: `SUG'URTA SHARTNOMASI № ...` и «СУҒУРТА ШАРТНОМАСИ № ...».
Эта формулировка стоит в **заголовках** ПКМ 1806 (uz) и Положения 3571, поэтому флаг `head`
на неё не ставился и правило заголовка её не разделяет. Узбекский договор страхования
опознаётся по любому второму реквизиту бланка (`seriya`, `polis raqami`, `shartnoma predmeti`,
`sug'urta obyekti`), а по одному голому заголовку — нет. Это не менялось.

**Флаг `"head": true` английским `insurance policy` и `insurance contract` — поставлен.**
Разработчик попросил убрать несимметрию: голый `INSURANCE CONTRACT` уходил в «прочее», тогда как
русский и узбекский аналоги опознавались. Риск здесь очевидный и тот же, что с «Тарифной
политикой»: `insurance contract` встречается в `book_Insurance_law.txt` 231 раз и в
`book_Reinsurance.txt` 207 раз, `insurance policy` — 65 и 26 раз. Поэтому решение принято не на
доводах, а на прогоне:

* оба английских учебника целиком — **«прочее» 0.000** (кандидаты договор 0.500, выписка 0.500),
  как и до флага;
* все 12 файлов `docs/source/*.txt` целиком — **«прочее» 0.000**, ни одного изменения против
  прогона без флага;
* те же 12 файлов, разрезанные по страницам (**1 893 страницы**, гораздо более жёсткая проверка:
  на каждой странице «первые три непустые строки» свои) — **0 срабатываний**;
* восемь коротких чужих документов и английские их аналоги (`CONTENTS / 1. Insurance policy … 5`,
  `INVOICE No. 12 / Insurance policy (service)`) — «прочее» 0.000;
* ранее опознаваемое не потеряно: полис ru 0.750, договор ru 1.000, `SUG'URTA POLISI` 1.000,
  «СУҒУРТА ПОЛИСИ» 1.000, `INSURANCE POLICY No.` 1.000, двуязычный бланк 0.750, все шесть видов
  на четырёх языках 1.000;
* приобретено: `INSURANCE CONTRACT No. 12` → договор **1.000**; `INSURANCE CONTRACT` + `Sum
  insured:` / `Insurance premium:` / `Period of insurance:` → договор **1.000**;
* `tests/test_ingest.py` — все проверки пройдены (число проверок печатает сам тест последней
  строкой; в заметке его не фиксируем — см. 8.4).

Почему истории «Тарифной политики» здесь не повторяется: новое правило само требует второго
признака бланка. Чтобы учебник получил вид, в его первых трёх непустых строках должна стоять
строка, где кроме `insurance contract` нет ни одного значащего слова, и при этом в той же строке
должен быть номер либо в первых 40 строках — две метки со значениями («Sum insured: 100 000 000»).
У оглавления и текста учебника ни того, ни другого нет: `1. Insurance contract ...... 20` — это
номер главы и номер страницы, но значащие слова `1` и `20` служебные, а второго признака нет,
поэтому строка не проходит проверку. Прогон это подтверждает — включая постраничный.

Честное ограничение флага: `INSURANCE CONTRACT` **без номера и без двух заполненных реквизитов**
остаётся «прочим» (кандидат договор 0.500). Симметрично русскому «СТРАХОВОЙ ПОЛИС / Ташкент».
Откатывать нечего — регрессий прогон не показал, но если реальный английский бланк компании
окажется без номера и без реквизитов, вид по нему поставит агент.

**Нужен ли флаг `"head": true` сильным маркерам техпаспорта, кадастра и выписки?** Разработчик
предложил проставить его для единообразия. Решение: **не ставить**, и вот почему. В условии
выше `head` — не ограничение, а вторая ветвь через `or`. У маркера с весом ≥ 4 первая ветвь
(`w >= 4 and where != "текст"`) уже покрывает все места, где стоит вторая, — флаг физически
ничего не изменит. Проверено прямым прогоном: флаг проставлен **56** маркерам техпаспорта,
кадастра и выписки, прогнаны 5 контрольных бланков (ru/en техпаспорт, ru/en кадастр, ru выписка
по лицевому счёту) и все 12 файлов `docs/source/*.txt` — **0 различий**. Учебники, нормативные
акты и коммерческое предложение остались «прочим» и с флагом, и без него. Ставить его — значит
завести в словаре поле, которое ни на что не влияет, но читается как «эти маркеры работают
только в заголовке», что неправда: `certificate of registration` в имени файла или в шапке
XLSX-листа засчитывается сильным и сейчас. Если правило когда-нибудь превратят в ограничение
(`head` → маркер силён **только** в строке-заголовке), возвращаться к этому надо будет с
отдельной проверкой — тогда флаг изменит поведение и техпаспорт из XLSX-выгрузки может
потеряться. После появления `_is_blank_title` решение только укрепилось: вторая ветвь теперь
**сужает** правило (нужны ещё и номер или два реквизита), так что флаг на маркере с весом ≥ 4
не был бы пустышкой — он мог бы отнять уже работающие случаи.

### 8.3.1. Список реквизитов бланка лежит в коде — предлагаю перенести в словарь

`ingest.BLANK_REQUISITE_LABELS` — **25 меток** (ru 10, uz-latn 6, uz-cyrl 3, en 6): страховая
сумма / премия / тариф, срок страхования, срок действия, период страхования, объект страхования,
страхователь, страховщик, выгодоприобретатель и их написания на узбекской латинице, узбекской
кириллице и по-английски. По смыслу это такой же словарь, как `doc_kinds`: перечень формулировок
на четырёх языках, а не алгоритм. Держать его в коде неудобно — при появлении реальных бланков
компании пополнять список придётся разработчику, а не аналитику.

**Согласен перенести его в `docs/ingest_dicts.json` отдельным разделом `blank_requisites`.**
Сам не переношу: это правка кода (`_blank_requisite_folded` должна читать словарь), ставится
отдельной задачей. Что остаётся в коде и переносу не подлежит: `BLANK_REQUISITES_MIN`,
`_BLANK_VALUE_RE` (разделитель + число), `_BLANK_SERVICE_RE`, `_BLANK_NUM_WORDS`, `_BLANK_NUM_SIGN`
— это правила разбора, а не термины.

Два условия переноса. Первое: список обязан остаться в **свёрнутом** виде (нижний регистр,
апостроф `'`), иначе `D.fold` даст несовпадение. Второе: узбекская кириллица в списке неполна —
там всего три метки против шести у латиницы (нет «суғурта объекти», «суғурта қилдирувчи»,
«суғурталовчи»). Добавлять их надо **вместе с переносом и с прогоном**: «суғурта объекти» стоит
в тексте Положения 3571, и хотя требование «метка + разделитель + число» её там не засчитывает,
проверять это надо прогоном, а не на словах.

### 9.1. У техпаспорта не было сильного узбекского маркера на официальное название СРТС

Было: `texnik pasport` → техпаспорт **1.000**, русское «свидетельство о регистрации транспортного
средства» и английское `vehicle registration certificate` — тоже 1.000, а официальное название
бланка `TRANSPORT VOSITASINI RO'YXATGA OLISH GUVOHNOMASI` и его кириллическое написание —
**«прочее» 0.000**: из узбекских написаний в словаре был только `guvohnoma` / «гувоҳнома»
с весом 2, то есть слабый.

Источник формулировок — ПКМ № 683 от 31.08.2017 (госрегистрация ТС,
`library/01_Законодательство/02_Акты_регуляторов/ПКМ № 683 …`, lex.uz/uz/docs/3334124) и
`docs/i18n_terms.json` → `doc_kinds` → техпаспорт (файл юриста, написание
`roʻyxatdan oʻtganlik guvohnomasi`). Добавлены шесть сильных маркеров (вес 4, по три на каждое
написание):

| uz-latn | uz-cyrl | откуда формулировка |
|---|---|---|
| `ro'yxatga olish guvohnomasi` | «рўйхатга олиш гувоҳномаси» | название бланка СРТС |
| `ro'yxatdan o'tganlik guvohnomasi` | «рўйхатдан ўтганлик гувоҳномаси» | `docs/i18n_terms.json` (юрист) |
| `ro'yxatdan o'tkazish haqida guvohnoma` | «рўйхатдан ўтказиш ҳақида гувоҳнома» | текст ПКМ № 683 (uz) |

Первый маркер намеренно записан **без слова `transport vositasini`**: так он покрывает и
`TRANSPORT VOSITASINI RO'YXATGA OLISH GUVOHNOMASI`, и `AVTOMOTOTRANSPORT VOSITASINI …` одной
строкой, а лишних маркеров в словаре не заводится.

Почему это не задевает водительское удостоверение: `haydovchilik guvohnomasi` / «ҳайдовчилик
гувоҳномаси» ни одного из шести маркеров не содержит — все они требуют перед `guvohnoma` слова
`ro'yxat…`. Проверено прогоном: «ҲАЙДОВЧИЛИК ГУВОҲНОМАСИ № АБ 1234567» остаётся «прочим» 0.000.
Отдельно проверено, что маркеры не совпадают со свидетельством о госрегистрации юрлица
(`davlat ro'yxatidan o'tganlik guvohnomasi` → в свёртке `royhatidan`, а не `royhatdan`).

### 9.2. Маркер «выписка из государственного реестра» не переживал вставленное слово

Маркер ищется **подстрокой**, поэтому «ВЫПИСКА ИЗ ГОСУДАРСТВЕННОГО РЕЕСТРА» давала выписку
1.000, а «ВЫПИСКА ИЗ **ЕДИНОГО** ГОСУДАРСТВЕННОГО РЕЕСТРА» — «прочее» 0.000 (совпадала одна
слабая «выписка», вес 3). Добавлено:

| Вид | Маркер | Язык | Вес |
|---|---|---|---|
| выписка | «выписка из единого государственного реестра» | ru | 5 |
| выписка | «выписка из реестра» | ru | 4 |
| выписка | `reyestrdan ko'chirma` | uz-latn | 4 |
| выписка | «реестрдан кўчирма» | uz-cyrl | 4 |
| кадастр | `extract from the unified state register` | en | 5 |
| кадастр | «выписка из единого государственного реестра» | ru | 2 |

Про узбекские написания честно: **пробела там не было**. Во-первых, `ko'chirma` / «кўчирма»
сами по себе сильные (вес 4), во-вторых, узбекский порядок слов ставит `yagona` перед маркером,
поэтому `YAGONA DAVLAT REYESTRIDAN KO'CHIRMA` совпадала с имеющимся `davlat reyestridan
ko'chirma` и до правки. Добавленные `reyestrdan ko'chirma` / «реестрдан кўчирма» закрывают
другое — написание **без притяжательного аффикса** (`YAGONA REYESTRDAN KO'CHIRMA`), которое
с имеющимися маркерами не совпадало. Дублирования весов нет: в свёртке `reyestrdan kochirma`,
`reestrdan kochirma` и `davlat reyestridan kochirma` — три разные строки (свёртка `ye → e`
работает только в начале слова, поэтому латинское `reyestr` и кириллическое «реестр» не
сливаются).

Последняя строка таблицы — не опечатка, а сохранение уже работавшего разбора пары
«кадастр / выписка». «Выписка из государственного реестра» есть и у вида «кадастр» (вес 2,
приходит из `docs/i18n_terms.json`), поэтому «ВЫПИСКА ИЗ ГОСУДАРСТВЕННОГО РЕЕСТРА ПРАВ НА
НЕДВИЖИМОЕ ИМУЩЕСТВО» + «Кадастровый номер: …» давала кадастр 1.000. Без парного маркера
написание с «единого» перевесило бы в «выписку», то есть словарная правка поменяла бы вид
документа — этого быть не должно. С ним прогон даёт **кадастр 1.000** в обоих написаниях.

Попутно замечено (код, не словарь, поэтому не трогал): в `ingest.detect_kind` правило разбора
пары «кадастр / выписка» ищет `kadastroviy nomer`, а `docparse.fold («кадастровый номер»)` даёт
`kadastrovыy nomer` — русское написание под правило не попадает никогда, работает только
`kadastr raqami`. Сейчас это незаметно, потому что вид совпадает и без правила. Отдельная задача
разработчику.
