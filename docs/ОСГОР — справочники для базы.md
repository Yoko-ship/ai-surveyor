## 1. Новая таблица: классификация видов деятельности (934 позиции)

Приложение № 9 к Правилам ПКМ № 177, раздел I, п. 3 (в ред. ПКМ № 443 от 15.07.2025).
Данные — `library/05_Методология/ОСГОР — классификация видов деятельности и коэффициенты КСТ (ПКМ 177, прил. 9).csv`
(разделитель `;`, кодировка UTF-8 с BOM, дробная часть КСТ через запятую).

```sql
-- Классификация видов деятельности работодателя и коэффициенты страховых тарифов (КСТ).
-- Прил. № 9 к Правилам ПКМ № 177, разд. I, п. 3 (ред. ПКМ № 443 от 15.07.2025): 934 вида
-- деятельности, 20 категорий профессионального риска, КСТ от 0,571 до 7,714.
-- Вид деятельности вне перечня → КСТ 3,400 (разд. I, п. 6), отдельной строкой не хранится.
CREATE TABLE IF NOT EXISTS osgor_activities (
    no        INTEGER PRIMARY KEY,       -- № позиции в перечне, 1..934
    category  INTEGER NOT NULL,          -- категория профессионального риска, 1..20
    kst       REAL NOT NULL,             -- коэффициент страхового тарифа
    okved     TEXT,                      -- код ОКЭД (IFUT)
    name      TEXT NOT NULL,             -- наименование вида деятельности
    act_ref   TEXT NOT NULL DEFAULT 'ПКМ № 177, прил. № 9, разд. I, п. 3 (ред. ПКМ № 443 от 15.07.2025)'
);
CREATE INDEX IF NOT EXISTS ix_osgor_activities_okved ON osgor_activities(okved);
```

Загрузка в `tools/db_build.py` — из того же CSV; `app/osgor.load_activities(con)` читает поля
`no, category, kst, okved, name` и сам падает обратно на CSV, если таблицы нет.

Контроль после загрузки: 934 строки, 20 различных категорий, `min(kst) = 0.571`, `max(kst) = 7.714`.

## 3. Продукт 1323 и минимальная премия

Строка `products` уже есть и менять её не нужно:
`('1323', 'ОСГОР работодателя', 'ПКМ №177', 'до 25%', 25.0, 'нормативный акт', 0, 'действует', …)`,
`product_classes = ('1323', '13', 1)`.

**Минимум в `min_rates` не помещается**: там минимум хранится в процентах от страховой суммы,
а по ОСГОР минимум — **абсолютная сумма 0,25 БРВ** (п. 23 Правил). Ставка же вообще не минимум,
а единственно допустимая величина: 0,1 % × КСТ.

Предлагаю (решает разработчик вместе с руководителем):
- строку в `min_rates` по продукту 1323 **не заводить**, чтобы движок случайно не сравнил
  нормативную ставку с «минимумом компании»;
- размер БРВ хранить в `app_settings`:

```
app_settings (key, value, updated_at) = ('BRV', '<размер БРВ в сумах>', '<дата>')
app_settings (key, value, updated_at) = ('BRV_FROM', '<дата вступления в силу>', '<дата>')
```

Значение БРВ я сознательно нигде не зашил: в проекте его до сих пор не было, а выдумывать
сумму, на которой считается минимальная премия, нельзя. **Вопрос заказчику** — какой размер БРВ
и с какой даты считать действующим (см. отчёт).

## 7. Чего в базе делать **не** надо

- Не заводить `coefficients` по классу 13: коэффициент один — КСТ из акта, он в `osgor_activities`.
  Экспертные множители оценки риска (условия труда, охрана труда, тяжесть) живут в коде
  `app/osgor.py` с пометкой `calibrated = 0` и в справочник коэффициентов не переносятся,
  пока не будет статистики компании.
- Не заводить `base_rates` по классу 13: базовая ставка 0,1 % — из акта, не из расчёта компании.
- Не калибровать тариф ОСГОР по убыткам: ставка задана нормативно (ЗРУ-210 ст. 8 ч. 4).
  Статистика по ОСГОР нужна только для аналитики и для резерва по ст. 22 ЗРУ-210.
