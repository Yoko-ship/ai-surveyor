# Как поднять систему на тестовом сервере за 15 минут

Для руководителя. Ничего программировать не нужно: всё делается мышкой в браузере.
Понадобятся: почта, карта не нужна (бесплатные тарифы), 15 минут.

> **ВАЖНО, прочитать до начала.**
> **На тестовый сервер за пределами Узбекистана нельзя загружать персональные данные граждан
> (ФИО, ПИНФЛ, паспорт, телефон, адрес конкретного человека). Только обезличенные примеры.**
> Это правило проекта № 8 и требование законодательства РУз о персональных данных.
> В системе для этого есть переключатель: **режим данных «test»** — тестовый сервер,
> **«prod»** — только сервер, физически расположенный в Узбекистане. По умолчанию стоит «test»,
> и переключить его на «prod» можно только с подтверждением.

---

## Шаг 0. Что уже готово в проекте

В корне проекта лежат файлы, которые площадки понимают сами:

| Файл | Зачем |
|---|---|
| `Dockerfile` | как собрать образ приложения; порт берётся из переменной `PORT` |
| `docker-compose.yml` | запуск на своём сервере одной командой `docker compose up -d` |
| `railway.json` | настройки для Railway |
| `render.yaml` | настройки для Render |
| `Procfile` | запасной вариант запуска (Heroku-совместимые площадки) |
| `.env.example` | список всех переменных с пояснениями |

Проверка живости у всех одна: адрес `/health` — он отвечает `{"status":"ok"}`.

## Вариант А. Railway (проще)

1. Открыть **railway.com** → кнопка **Login** → войти через GitHub.
2. Код проекта должен быть в репозитории GitHub. Если его там ещё нет — попросите разработчика
   загрузить (это 5 минут) или используйте вариант «Deploy from local» в их инструкции.
3. На главной странице Railway нажать **New Project** → **Deploy from GitHub repo** → выбрать репозиторий проекта.
4. Railway сам увидит `Dockerfile` и `railway.json` и начнёт сборку. Ждать 3–5 минут,
   пока в логе не появится строка `Uvicorn running`.
5. Слева выбрать сервис → вкладка **Variables** → **New Variable**. Добавить по одной (см. таблицу ниже).
6. Вкладка **Settings** → раздел **Networking** → **Generate Domain**. Railway выдаст адрес
   вида `имя-проекта.up.railway.app` — это и есть ссылка на систему.
7. Открыть `https://<ваш адрес>/health` — должно быть `{"status":"ok"}`.
   Затем `https://<ваш адрес>/` — главная страница.

## Вариант Б. Render

1. Открыть **render.com** → **Get Started** → войти через GitHub.
2. Кнопка **New +** → **Web Service** → **Build and deploy from a Git repository** → выбрать репозиторий.
3. В настройках выбрать **Language: Docker** (Render подхватит `Dockerfile`), план — **Free**.
   Поле **Health Check Path** заполнить: `/health`.
4. Раздел **Environment Variables** → **Add Environment Variable**: добавить переменные из таблицы ниже.
5. Кнопка **Create Web Service**. Сборка 5–10 минут. Адрес будет вида `имя.onrender.com`.
6. Проверить `/health`.

> На бесплатном тарифе Render сервис «засыпает» после 15 минут без обращений
> и просыпается 30–60 секунд. Для показа это нормально, для работы — нет.

## Какие переменные вписать

Минимум, чтобы всё работало, — **ничего**. Система поднимется и без единой переменной:
ИИ будет выключен, вход — по логину и паролю.

| Переменная | Что вписать | Обязательно? |
|---|---|---|
| `PD_MODE` | `test` | да (защита от загрузки персональных данных) |
| `SERVER_URL` | адрес, который выдала площадка, например `https://inson.up.railway.app` | желательно |
| `LLM_PROVIDER` | `kimi`, если подключаем ИИ; иначе `none` | нет |
| `LLM_BASE_URL` | `https://api.moonshot.ai/v1` | только с `kimi` |
| `LLM_MODEL` | `kimi-k3` | только с `kimi` |
| `LLM_API_KEY` | ключ из личного кабинета Moonshot (см. ниже) | только с `kimi` |
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather | только для мини-приложения |
| `DATABASE_URL` | пока пусто — заготовка под PostgreSQL | нет |

То же самое можно ввести и в самой системе: страница **«Запуск и обслуживание»** (`/admin/deploy`).
Значения, введённые там, важнее переменных площадки — так ключ можно поменять, не трогая сервер.
Ключи на странице показываются только маской вида `sk-...abcd`: целиком их не видит никто.

## Где взять ключ Kimi (Moonshot)

1. Открыть **platform.moonshot.ai** → **Sign up** (регистрация по почте или через Google).
2. В кабинете найти раздел **API Keys** → кнопка **Create API Key** → придумать название (например, `INSON`).
3. Ключ показывается **один раз** — скопировать и сохранить в надёжном месте (не в переписке и не в репозитории).
4. Пополнить баланс в разделе **Billing**: для проверки хватает минимальной суммы;
   без денег на счёте запросы будут отклоняться с сообщением «превышен лимит».
5. Вписать ключ в `LLM_API_KEY` (или на странице `/admin/deploy`) и нажать **«Проверить»**
   в блоке «Искусственный интеллект» на странице `/admin`. Должно появиться «Связь есть».

Если ключа нет — ничего страшного: расчёт, проверки, документы, отчёты работают полностью.
Без ИИ объяснение расчёта клиенту собирается по шаблону, а поля документов ищутся одними правилами.

Адрес и название модели взяты из официальной документации Moonshot (проверено 20.09.2026:
в примере запроса указан `"model": "kimi-k3"`, адрес `https://api.moonshot.ai/v1`).
Названия моделей у поставщиков меняются — если появится ошибка «адрес или название модели неверны»,
посмотрите актуальный список на platform.moonshot.ai/docs/pricing.

## Про сохранность данных: читать обязательно

**На бесплатных тарифах Railway и Render диск не сохраняется между перезапусками.**
Каждое обновление кода, перезапуск или «засыпание» сервиса означает, что файл базы
`data/surveyor.db` вернётся к тому состоянию, в котором его собрали при сборке образа:
все введённые запросы, загруженные документы и настройки пропадут.

Что с этим делать:

1. **Для показа и обучения** это допустимо: справочники (176 продуктов, коэффициенты, правила)
   собираются при сборке заново, поэтому система всегда рабочая — теряются только введённые данные.
2. **Резервные копии.** На странице `/admin/deploy` кнопка «Сделать копию» собирает архив
   (база + загруженные файлы) и даёт его скачать. Перед каждым обновлением — сделать копию
   и скачать себе. Восстановление: та же страница, кнопка «Восстановить», требует подтверждения.
   То же из командной строки: `python tools/backup.py` и `python tools/restore.py <файл> --да`.
3. **Платный диск.** На Render это Disk (раздел Disks, ~1 ГБ), на Railway — Volume,
   смонтированный в `/srv/data`. Стоит несколько долларов в месяц и решает проблему.
4. **PostgreSQL** — правильное решение для промышленной эксплуатации: база живёт отдельно от
   приложения и переживает любые перезапуски. Это отдельная работа (см. ниже), и делать её
   нужно до того, как в системе появятся настоящие договоры.

**И главное: боевая эксплуатация с настоящими данными клиентов — только на сервере в Узбекистане.**
Railway и Render — площадки зарубежные, поэтому они годятся исключительно для тестового показа
на обезличенных примерах.

## Что придётся поправить при переходе на PostgreSQL

Система с самого начала пишется так, чтобы переезд не означал переписывания логики.
Проверка выполняется сама: страница `/admin/deploy` → «Проверить схему»
(или `python tools/schema_check.py`). На 20.09.2026 она показывает:

**Что обязательно поправить (ошибки):**

1. `INTEGER PRIMARY KEY` — в SQLite такая колонка нумеруется сама, в PostgreSQL нет.
   Заменить на `GENERATED BY DEFAULT AS IDENTITY` (около 30 таблиц, механическая правка).
2. `INSERT OR REPLACE` / `INSERT OR IGNORE` — синтаксис только SQLite.
   В PostgreSQL: `INSERT ... ON CONFLICT (...) DO UPDATE/DO NOTHING` (несколько мест в `app/main.py`,
   `app/team.py`, `app/knowledge.py`, `tools/db_build.py`, `tools/market_stats.py`).
3. Функции даты `datetime('now')`, `strftime()` — в PostgreSQL это `now()`, `to_char()`
   (`app/portfolio.py`, `app/proposal.py`, `app/team.py`, `app/valuation.py`, `tools/library_build.py`).
4. Параметры запросов сейчас подставляются знаком `?`, драйверу PostgreSQL нужен `%s`.
   Это правится **один раз** в `app/db.py` (обёртка вокруг `execute`), а не в каждом запросе.
5. Прямое обращение к `sqlite3` в нескольких скриптах (`tools/db_build.py`, `tools/market_stats.py`,
   `tools/ui_build.py`, `tools/lex_fetch.py`, `app/stat_sources.py`) — перевести на общий слой `app/db.py`.

**Что стоит поправить (предупреждения):**

6. Даты хранятся строками (ISO-текст) — перевести в тип `TIMESTAMP`, иначе сравнение дат
   работает как сравнение строк.
7. Признаки «да/нет» хранятся числами 0/1 — в PostgreSQL удобнее тип `BOOLEAN`.
8. `lastrowid` (получение номера только что вставленной строки) — заменить на `INSERT ... RETURNING id`.
9. `PRAGMA` — только SQLite, убрать.

Драйвер PostgreSQL (`psycopg`) намеренно **не установлен**: ставить его будем тогда,
когда заказчик выберет, где стоит база (собственный сервер в Узбекистане или облако местного провайдера).
Переменная `DATABASE_URL` уже заведена во всех файлах настроек — останется только вписать адрес.

## Свой сервер (если база должна стоять в Узбекистане)

На сервере с Docker:

```
docker compose up -d          # запуск
docker compose logs -f        # что происходит
docker compose down           # остановить
```

Данные (база, документы, фото, отчёты, резервные копии) лежат в томе `surveyor-data`,
подключённом к `/srv/data`, и переживают перезапуски и обновления.
Настройки берутся из файла `.env` (скопировать из `.env.example` и заполнить).

## Куда смотреть, если что-то не так

| Симптом | Что проверить |
|---|---|
| Страница не открывается | адрес `/health`; в логе площадки строка `Uvicorn running` |
| `/health` отвечает, страницы пустые | база не собралась: в логе сборки строка `python tools/db_build.py` |
| ИИ не отвечает | `/admin` → блок «Искусственный интеллект» → «Проверить»; текст ошибки написан по-русски |
| Вход через Telegram не работает | не задан `TELEGRAM_BOT_TOKEN` — система честно пишет «режим браузера» |
| Данные пропали после обновления | бесплатный тариф без диска — см. раздел о сохранности данных выше |
